# Трекер звичок

Вебзастосунок і Telegram-бот працюють з одним FastAPI API та SQLite.
У кожної людини власні звички, відмітки, календар, серії та аналітика.
Фронтенд: React + TypeScript + Vite; бот: aiogram з polling.

```text
Браузер ────────┐
                ├── FastAPI API ── SQLite
Telegram-бот ───┘
```

## Локальний запуск

Потрібні Python 3.14 і Node.js 22. Команди нижче для PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
Copy-Item .env.example .env
```

Копіюй `.env.example` лише перед першим налаштуванням, коли `.env` ще немає.
Заповни `BOT_TOKEN`, `BOT_SECRET`, `BOT_USERNAME` і `SESSION_SECRET` у `.env`.
Секрети згенеруй окремо для двох змінних:

```powershell
.\.venv\Scripts\python.exe -c "import secrets; print(secrets.token_hex(32))"
```

Збери фронтенд:

```powershell
cd frontend
npm ci
npm run build
cd ..
```

Запусти API, а в окремому терміналі — бота:

```powershell
.\.venv\Scripts\python.exe -m uvicorn main:app --reload --port 8000
```

```powershell
.\.venv\Scripts\python.exe -m bot
```

Відкрий [вебзастосунок](http://127.0.0.1:8000/app/). Корінь `/` переадресовує
сюди. FastAPI віддає результат збірки з `frontend/dist`; якщо його немає,
`/app/` повертає `503` із поясненням, що потрібно зібрати.

Для розробки фронтенду запусти `npm run dev` у `frontend/` і відкрий
[Vite](http://localhost:5173). API на порту 8000 теж має працювати: Vite
проксіює до нього запити.

## Вхід і налаштування

На сторінці натисни «Увійти через Telegram», відкрий посилання бота й
підтвердь вхід. Браузер обміняє одноразовий код на підписану cookie й покаже
той самий акаунт, що й бот. API не надсилає повідомлень до Telegram: код
підтверджує запущений бот. Запит до особистих даних без входу отримує `401`.

| Змінна | Призначення |
|---|---|
| `BOT_TOKEN` | Токен від [@BotFather](https://t.me/BotFather) |
| `BOT_USERNAME` | Ім'я бота без `@`, для посилання входу |
| `BOT_SECRET` | Спільний випадковий ASCII-секрет API й бота |
| `SESSION_SECRET` | Окремий випадковий секрет для підпису сесій |
| `SESSION_COOKIE_SECURE` | `false` для локального HTTP; `true` для HTTPS |
| `API_URL` | Адреса API для бота; локально `http://127.0.0.1:8000` |
| `DATABASE_URL` | SQLite URL; порожнє значення використовує `sqlite:///habits.db` |
| `BACKUP_DIR` | Тека щоденних копій; порожнє значення вимикає їх поза Compose |
| `TZ` | Системний пояс контейнерів і логів, стандартно `Europe/Kyiv` |
| `ALLOW_LOCAL_USER` | Лише для розробки: `1` відкриває окремий локальний акаунт без входу |

`ALLOW_LOCAL_USER` за замовчуванням вимкнено, а в Compose явно задано `false`.
Локальний акаунт має власні дані: він не підміняє Telegram-акаунт. Зміна
`SESSION_SECRET` відкликає видані сесії. `.env` не входить у Git та Docker-образ;
Compose передає необхідні значення через оточення.

## Звички, розклад і нагадування

- Під час створення можна вибрати дату початку й дні тижня. Щоденний
  розклад — усі сім днів; у API `0` означає понеділок, `6` — неділю.
- Серії та частка виконання враховують заплановані дні. Вихідний у розкладі
  не розриває серію. День визначає часовий пояс людини, а не браузера чи сервера.
- Архівація прибирає звичку зі щоденного списку та нагадувань і зберігає
  історію. З архіву її можна повернути. Видалення назавжди прибирає і звичку,
  і її відмітки.
- У налаштуваннях профілю можна змінити часовий пояс, годину нагадувань
  (`0`–`23`) і ввімкнути або вимкнути їх. Для наявних акаунтів міграція
  зберігає щоденні нагадування: `Europe/Kyiv`, 20:00, увімкнено.
- Бот перевіряє особистий розклад, нагадує лише про невиконані заплановані
  звички й зберігає день успішного надсилання в БД. Після перезапуску він
  знає, за який день повідомлення вже надіслано.
- Експорт JSON завантажує всі власні звички, включно з архівом, і всю
  історію відміток. Це персональний експорт; для відновлення всього сервера
  використовуй SQLite-копію нижче.

Дата початку й дні тижня задаються під час створення; зміна історичного
розкладу окремими періодами поки не підтримується. Для нового розкладу
можна архівувати стару звичку й створити нову.

## Docker і публікація через HTTPS

Заповни чотири обов'язкові значення `.env`: `BOT_TOKEN`, `BOT_SECRET`,
`BOT_USERNAME`, `SESSION_SECRET`. Без них Compose пояснить, чого бракує.

```bash
docker compose up -d --build
docker compose ps
docker compose logs -f bot
docker compose down
```

Обидва сервіси збираються з одного Dockerfile. Фронтенд збирається окремим
етапом, а API й бот працюють від непривілейованого користувача. Бот стартує
після успішної перевірки `/health`, яка перевіряє доступність SQLite.
`restart: unless-stopped` відновлює роботу після перезапуску Docker.

База `/data/habits.db` і копії `/data/backups` лежать на іменованому томі
`habits-data`. Звичайний `docker compose down` зберігає том.
**`docker compose down --volumes` видаляє дані**, тому ця команда придатна
лише для одноразового тестового середовища.

Порт API прив'язаний до `127.0.0.1:8000`. Для публічного вебдоступу постав
перед ним reverse proxy з HTTPS і встанови `SESSION_COOKIE_SECURE=true`.
Для локального HTTP залиш `false`, інакше браузер не надсилатиме cookie.
Підтвердження через Telegram залишається способом входу в обох випадках.

Сам бот використовує polling і потребує постійно запущеного процесу з
вихідним доступом до Telegram; webhook йому не потрібен. Запускай один
екземпляр бота й один API з постійним локальним SQLite-томом.

## Міграції та резервні копії

Під час старту API `migrations.upgrade(engine)` читає `PRAGMA user_version`.
Нова порожня база одразу отримує актуальні таблиці та версію `1`.
Для підтримуваної старої схеми з таблицями користувачів, звичок і відміток
перед змінами створюється узгоджена SQLite-копія:

```text
<тека бази>/backups/<назва бази>.pre-v1-<унікальний код>.sqlite3
```

Копіювання використовує SQLite backup API, тому охоплює і збережені дані
у WAL. Копія проходить `PRAGMA integrity_check`. Якщо створити чи перевірити
її не вдалося, схема не змінюється й старт API завершується помилкою.
Міграція виконується в транзакції з перевіркою схеми, цілісності та зовнішніх
ключів. Повторний старт не повторює оновлення й не перезаписує копію.
Версія БД новіша за код зупиняє старт із поясненням.

Міграція зберігає ID, власників і відмітки. Початок старої звички береться
з найпершої відмітки; якщо відміток немає — з поточної дати `Europe/Kyiv`.
Для старих звичок встановлюється щоденний розклад. Дуже стара схема без
таблиці користувачів потребує окремого переходу; автоматичне призначення
власника не виконується.

`BACKUP_DIR` вмикає додаткові щоденні копії. API перевіряє їх на старті й
щогодини, створюючи не більше однієї копії на UTC-день:
`<назва бази>.daily-YYYY-MM-DD.sqlite3`. Compose використовує `/data/backups`.
Наявна копія перевіряється; попередні копії автоматично не видаляються.
Готовий файл з'являється лише після перевірки й синхронізації тимчасової
копії. Аварійно залишений `.backup-*.sqlite3.tmp` не блокує повторну спробу.
Публікація потребує файлової системи з підтримкою hard link (наприклад,
NTFS або ext4); якщо вона недоступна, операція завершується помилкою.
Передміграційна копія створюється незалежно від `BACKUP_DIR`.
Для захисту від втрати диска регулярно перенось готові копії на окремий носій.

Для ручного копіювання й відновлення є CLI без типового шляху до БД:

```bash
python -m backups backup --source /data/my-tracker.sqlite3 --destination /safe-storage/snapshot-2026-09-12.sqlite3
python -m backups restore --source /safe-storage/snapshot-2026-09-12.sqlite3 --destination /data/restored-2026-09-12.sqlite3
```

Підстав свої явні шляхи. У Windows вони можуть мати вигляд
`C:\TrackerData\my-tracker.sqlite3`. Тека призначення має існувати,
а сам файл і його SQLite sidecar-файли (`-wal`, `-shm`, `-journal`) — ні.
CLI відкриває джерело лише для читання, перевіряє цілісність і не перезаписує
існуючі файли. Помилка дає ненульовий код завершення.

Порядок відновлення:

1. Зупини API й бота.
2. Віднови обрану копію в **новий файл** через `python -m backups restore`.
3. Зміни `DATABASE_URL` на новий файл і запусти API; в Compose для цього
   зміни `services.api.environment.DATABASE_URL`, зберігаючи шлях на `/data`.
4. Перевір `/health`, увійди й перевір історію, після чого запусти бота.

Для виконання CLI з доступом до Docker-тому можна використати
`docker compose run --rm --no-deps api python -m backups ...` з явними
шляхами всередині `/data`. Збережи початковий файл до перевірки результату.
Файли `.env`, `habits.db` і наявні `habits.db*` не можна змінювати чи
видаляти під час розробки й тестування.

## API

[OpenAPI](http://127.0.0.1:8000/docs) описує повний контракт. Особисті
ендпоїнти потребують cookie сесії або перевірених заголовків бота.

| Метод | Шлях | Опис |
|---|---|---|
| `GET` | `/health` | Готовність API та БД, без входу |
| `POST` | `/auth/login-code` | Видати одноразовий код для входу |
| `GET` | `/auth/login-code/{token}` | Очікувати підтвердження й отримати сесію |
| `POST` | `/auth/confirm` | Підтвердити код; лише бот |
| `POST` | `/auth/logout` | Вийти з вебакаунта |
| `GET`, `PATCH` | `/users/me` | Профіль, часовий пояс і нагадування |
| `GET` | `/users/me/today` | Поточна дата в поясі користувача |
| `GET` | `/users/me/export` | Повна особиста історія в JSON |
| `GET`, `POST` | `/habits` | Список і створення; `include_archived=true` включає архів |
| `GET`, `PATCH`, `DELETE` | `/habits/{id}` | Перегляд, назва/опис/`archived`, видалення |
| `GET`, `POST` | `/habits/{id}/checkins` | Відмітки; фільтри `since` й `until` |
| `DELETE` | `/habits/{id}/checkins/{day}` | Зняти відмітку |
| `GET` | `/habits/{id}/stats` | Статистика звички |
| `GET` | `/stats` | Статистика всіх звичок; також `include_archived` |

Бот надсилає `X-Telegram-Id` і `X-Bot-Secret`; саме секрет підтверджує право
назвати користувача. Імена передаються JSON, адже HTTP-заголовки не підходять
для кирилиці. Доступ до чужої звички повертає `404`.

## Перевірки

Python-тести використовують свіжі тимчасові бази й підміну залежностей;
сервер запускати не потрібно. Оточення нижче також вимикає читання `.env`
і задає безпечну базу для імпорту застосунку:

```powershell
$env:PYTHON_DOTENV_DISABLED = '1'
$env:DATABASE_URL = 'sqlite://'
.\.venv\Scripts\python.exe -m pytest -q
```

```bash
cd frontend
npm ci
npx tsc --noEmit
npm test
npm run build
```

CI окремо запускає Python-тести, перевірки фронтенду та Compose з API на
одноразовому томі. Останній перевіряє `/health`, зібрану `/app/`, видачу
коду входу та `401` для неавторизованого доступу. Бот у цьому тесті не
запускається, використовуються лише вигадані секрети.

## Структура й межі

| Файл або тека | Роль |
|---|---|
| `main.py`, `auth.py` | API, вхід, перевірка власника |
| `models.py`, `stats.py` | Дані, валідація, серії та статистика |
| `database.py`, `migrations.py`, `backups.py` | SQLite, версії схеми, резервування |
| `config.py`, `.env.example` | Налаштування оточення |
| `bot/` | HTTP-клієнт, команди, діалоги, нагадування |
| `frontend/src/` | Екрани, API-хуки, компоненти й аналітика |
| `test_*.py`, `frontend/src/**/*.test.*` | Регресійні та контрактні тести |

Бот звертається до API через асинхронний HTTP, щоб синхронні SQLite-запити
не блокували його event loop. Обидва інтерфейси ділять правила й дані.

Незавершені діалоги бота зберігаються в пам'яті, тому перезапуск їх обриває.
Експорт JSON не має зворотного імпорту. Копії на тому самому диску не
захищають від втрати носія; автоматичного очищення старих копій немає.
