# Трекер звичок

Відстеження щоденних звичок з **двома інтерфейсами до одного бекенду**:
вебсторінка й Telegram-бот. Список звичок, відмітки виконання по днях,
підрахунок серій, календар-хітмапа на 12 тижнів.

Навчальний проєкт: FastAPI + SQLite + aiogram.

```
                  ┌──────────────┐
    браузер ─────▶│              │
                  │  FastAPI API │──▶ SQLite
    Telegram ────▶│              │
      (бот)       └──────────────┘
```

## Запуск

```bash
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

**Бекенд** (потрібен завжди):

```bash
.venv\Scripts\python.exe -m uvicorn main:app --reload --port 8000
```

Далі відкрити http://127.0.0.1:8000/ — база `habits.db` створиться сама.

**Бот** (окремий термінал):

```bash
.venv\Scripts\python.exe -m bot
```

Перед першим запуском бота треба скопіювати `.env.example` у `.env`
і заповнити:

| Змінна | Звідки взяти |
|---|---|
| `BOT_TOKEN` | [@BotFather](https://t.me/BotFather) → `/newbot` |
| `BOT_SECRET` | `python -c "import secrets; print(secrets.token_hex(32))"` |
| `API_URL` | адреса бекенду, за замовчуванням `http://127.0.0.1:8000` |

`.env` у git не потрапляє. Бот перевіряє налаштування на старті
й пояснює, чого саме бракує.

## Тести

```bash
.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.venv\Scripts\python.exe -m pytest -q
```

158 тестів, близько 25 секунд. Працюють з тимчасовою базою й не торкаються
`habits.db`. Сервер для них запускати не треба — навіть для тестів бота.
Кілька тестів навмисно імітують гонку (два натискання «одночасно» через
`asyncio.gather`) — саме так знайшлися дві помилки, описані нижче.

Фронтенд має власні 40 тестів (`cd frontend && npm test`) — вони
перевіряють роботу з датами, обчислення для графіків і оптимістичну
арифметику відмітки.

## API

Інтерактивна документація — http://127.0.0.1:8000/docs

| Метод | Шлях | Опис |
|---|---|---|
| `GET` | `/users/me` | хто я з погляду API |
| `PATCH` | `/users/me` | зберегти ім'я |
| `GET` | `/habits` | список своїх звичок |
| `POST` | `/habits` | створити звичку |
| `GET` | `/habits/{id}` | одна звичка |
| `PATCH` | `/habits/{id}` | змінити назву чи опис |
| `DELETE` | `/habits/{id}` | видалити звичку та її відмітки |
| `GET` | `/habits/{id}/checkins` | відмітки; фільтри `?since=` та `?until=` |
| `POST` | `/habits/{id}/checkins` | відмітити день (без тіла — сьогодні) |
| `DELETE` | `/habits/{id}/checkins/{day}` | зняти відмітку |
| `GET` | `/habits/{id}/stats` | статистика однієї звички |
| `GET` | `/stats` | статистика всіх звичок одним запитом |

## Вебзастосунок

Фронтенд — окремий проєкт у теці `frontend/`: React 19 + TypeScript,
збирається Vite. FastAPI віддає вже зібрані файли з `frontend/dist`
за адресою `/app/`; у git вони не потрапляють.

```bash
cd frontend
npm install          # один раз
npm run dev          # розробка: http://localhost:5173, запити йдуть у проксі на :8000
npm run build        # бойова збірка у frontend/dist
npm test             # 40 тестів (Vitest)
```

Для `npm run dev` потрібен запущений `uvicorn` на порту 8000 — Vite
проксіює на нього `/habits`, `/stats`, `/auth` та інші шляхи API.
Якщо `frontend/dist` немає, `/app/` віддає `503` зі вказівкою, що
зібрати, — замість того щоб уронити застосунок на старті.

Що всередині:

- **TanStack Query** тримає серверні дані. Відмітка застосовується
  оптимістично: кнопка перемикається одразу, а відповідь сервера лише
  підтверджує вже намальоване. Помилка — і кеш відкочується до знімка.
- **Темна тема** зроблена на CSS-змінних: перемикач міняє єдиний
  атрибут `data-theme` на `<html>`. Вибір застосовується вбудованим
  у `index.html` скриптом ще до завантаження React — інакше в темряві
  був би спалах білим.
- **Аналітика** вантажиться окремим шматком (`React.lazy`): бібліотека
  графіків більша за решту застосунку, і платити за неї має лише той,
  хто відкрив вкладку. Основний бандл — 89 КБ у gzip, аналітика — ще 116 КБ.
- **Обчислення для графіків** винесені в `analytics/compute.ts` без
  React і мережі — за тим самим принципом, що й `stats.py` на бекенді:
  складне має перевірятися тестом, а не очима в браузері.

## Рішення, які варто пояснити

**Бот ходить у власне API по HTTP, а не в базу.** Робота з базою тут
синхронна; якби async-бот звертався до неї напряму, кожен запит блокував
би event loop — асинхронність лишилася б тільки в назві. HTTP-запит же
є очікуванням мережі, тобто саме тим, на чому asyncio виграє. Заразом
виходить чиста межа: один бекенд, два незалежні клієнти.

**Автентифікація бота — спільний секрет.** Бот додає до кожного запиту
`X-Telegram-Id` (кого обслуговує) і `X-Bot-Secret` (доказ, що це справді
він). Без другого перший нічого не вартий: інакше будь-хто назвався б
чужим номером. Порівняння секрету йде через `secrets.compare_digest`,
щоб час відповіді не підказував, де саме розбіжність.

**Ім'я користувача передається тілом JSON, а не заголовком.**
HTTP-заголовки за стандартом однобайтові, і «Олена» їх ламає. Це
закріплено тестом `test_cyrillic_in_header_is_impossible`.

**Чужа звичка дає 404, а не 403.** 403 означало б «існує, але не твоя»,
і перебором id можна було б порахувати чужі записи. 404 не каже нічого.

**Подвійний тап по звичці не ронить сервер.** `find_checkin` перед
вставкою не рятує від гонки: два запити можуть обидва пройти перевірку
до того, як перший зробить `commit`. Другий тоді впирається в
`UNIQUE(habit_id, day)` уже під час запису — і без обробки це була б
`500` замість чесної `409`. `create_checkin` ловить саме цей
`IntegrityError`. Перевірено прямим прогоном: до фіксу — 2 збої на
10 подвійних тапів, після — 0 на 10 (і 0 на 20 через справжній HTTP).

**Тап по звичці посеред діалогу створення не «закриває» його тихо.**
Кнопка звички ніяк не привʼязана до стану FSM, тож без перевірки вона
перемальовувала б звичайний список — найсильніший сигнал «діалог
скінчився» — хоча стан лишався на кроці `NewHabit.name`. Наступне ж
побутове повідомлення людини тихо ставало назвою нової звички.
`toggle_checkin` тепер питає стан і, якщо діалог триває, відмовляє
з проханням `/cancel` — той самий принцип, що вже стояв на командах.

**Подвійний клік «Пропустити» серіалізований локом.** Без нього два
майже одночасні виклики `finish()` могли обидва прочитати той самий
стан ДО того, як перший його прибере: другий бачив порожні дані й
казав людині «діалог загубився», хоча перший щойно все створив.
Лок на пару (чат, користувач) у `new_habit.py` це прибирає.

**`finish()` створює звичку ДО того, як прибрати стан.** У зворотному
порядку збій `create_habit` (обрив мережі, API ліг) стирав би назву
й опис разом зі станом — а порада «спробуй ще раз» ставала нездійсненною,
бо наступне повідомлення падало б у порожнечу.

**Ім'я з Telegram екранується перед HTML-текстом.** Бот працює з
`parse_mode=HTML` на весь застосунок, а `first_name` людина вписує
собі сама — символ «<» у нікнеймі («Ann<3») цілком реальний. Без
екранування Telegram відхиляв би геть КОЖЕН `/start` такої людини
назавжди, поки вона не перейменується. `views.py` вже уникав цієї
пастки для назв звичок — тепер той самий захист є й для чужого рядка,
яким є ім'я користувача.

**`BOT_SECRET` не з латиниці зупиняє старт із поясненням, а не
ламає все мовчки.** HTTP-заголовки за стандартом однобайтові (та сама
пастка, що з іменем користувача, тільки без цього секрет не стосується
жодного окремого повідомлення — він їде в заголовок X-Bot-Secret
щоразу). Непорожній кириличний секрет проходив би повз перевірку на
порожнечу мовчки, а перша ж дія в боті падала б голим
`UnicodeEncodeError` без жодного натяку на причину.

**Логіка окремо від інфраструктури.** `stats.py` не імпортує ні FastAPI,
ні SQLModel — лише роботу з датами. Тому його тести виконуються за 0.03 с
і не потребують ні бази, ні сервера.

**Серія не рветься опівночі.** `current_streak` вважається живою, якщо
відмічено сьогодні *або* вчора. Інакше двадцятиденний прогрес згорав би
о 00:01 за те, що людина ще спить.

**Унікальність продубльована в базі.** Ендпоінт перевіряє повтор і віддає
`409`, але обмеження `UNIQUE (habit_id, day)` стоїть і на рівні таблиці:
код можна випадково зламати при рефакторингу, базу — ні.

**`GET /stats` не масштабує кількість SQL-запитів.** Скільки б не було
звичок, їх лишається три: один на пошук користувача і два на дані.
Закріплено тестом `test_all_stats_does_not_scale_queries_with_habits`,
який лічить звернення до бази.

**Тести бота не піднімають сервер.** `httpx.ASGITransport` викликає
застосунок напряму в тому ж процесі. На відміну від моків, це перевіряє
справжній контракт: перейменують поле у відповіді — тест почервоніє.

**Обробники теж під тестами.** `test_bot_handlers.py` проганяє справжні
оновлення Telegram крізь диспетчер із сесією, яка замість надсилання
записує виклики. Так перевіряються роутери, фільтри й порядок обробників —
речі, яких тести клієнта не бачать. Два регресійні тести там стережуть
помилки, знайдені саме таким прогоном: команда посеред діалогу ставала
назвою звички, а стара кнопка лишалася без відповіді й вішала «годинник».

**День для зняття відмітки береться з `date.today()`, а не з `last_day`.**
Виглядало логічним спитати сервер, який день він вважає останнім
відміченим. Але `last_day` — це `max()` з усіх відміток без обмеження
зверху, а API приймає й майбутні дати. Відмітка на день наперед, поставлена
у браузері, зробила б `last_day` майбутнім — і бот видалив би не той запис.
Закріплено тестами; бот і API все одно ділять одну машину й один годинник.

**404 перекладається в людський текст лише там, де він однозначний.**
Для запиту до самої звички 404 означає рівно одне — звички немає.
А от при знятті відмітки той самий код означає або відсутню звичку,
або відсутню відмітку, тож зводиться до `False`. Розрізняти їх за текстом
поля `detail` було б крихко: досить переформулювати повідомлення на боці
API, і бот мовчки почне поводитись інакше.

## Docker

```bash
cp .env.example .env      # і заповнити BOT_TOKEN та BOT_SECRET
docker compose up -d --build
docker compose logs -f bot
```

Піднімаються два контейнери з одного образу: `api` (uvicorn) і `bot`
(polling). База лежить на іменованому томі `habits-data`, тож переживає
і перезбирання образу, і перезапуск.

**Часовий пояс задається обом контейнерам однаково** (`TZ` у `.env`,
за замовчуванням `Europe/Kyiv`). Це не косметика: бот і API кожен рахує
«сьогодні» за своїм годинником. Поки обидва на одній машині, це той
самий годинник — але в Docker за замовчуванням UTC, і «20:00»
перетворилося б на 23:00 за Києвом, а вечірня відмітка могла б лягти
на «завтра» з погляду одного з них. Бот друкує свій годинник у лог
на старті — щоб перевірити було чим, а не гадати.

Порт API прив'язаний до `127.0.0.1` навмисно: у нього немає входу
з паролем, тож відкривати його в інтернет не можна (див. «Обмеження»).

## Деплой

Бот працює на **polling** — сам питає Telegram, чи є новини. Для сервера
це означає, що не потрібні ні HTTPS, ні біла IP-адреса, ні webhook:
досить машини з інтернетом і Docker.

```bash
git clone <репозиторій> && cd Traker
cp .env.example .env      # заповнити токен і секрет
docker compose up -d --build
```

`restart: unless-stopped` подбає про перезапуск після падіння
й перезавантаження сервера.

**Безкоштовні тарифи здебільшого не підійдуть.** Render, Railway та
подібні присипляють контейнер без вхідного трафіку — а бот на polling
має працювати безперервно, і нагадування о 20:00 у сплячому контейнері
просто не спрацює. Потрібен постійно ввімкнений процес: найдешевший VPS
або Fly.io з `min_machines_running = 1`.

Webhook знадобиться, якщо колись з'явиться потреба масштабувати бота
на кілька екземплярів або якщо провайдер заборонить довгі вихідні
з'єднання. Для одного контейнера polling простіший і надійніший.

## Обмеження

- Вебінтерфейс працює в локальному режимі: запит без заголовків
  автоматично стає «локальним користувачем». Розраховано на запуск
  на localhost. Перед виставленням API назовні цей режим треба
  або вимкнути, або закрити справжнім входом із паролем.
- Стан діалогів бота живе в оперативній пам'яті (`MemoryStorage`),
  тож перезапуск обриває незавершене створення звички. У продакшені —
  `RedisStorage`.
- SQLite на одному томі означає один екземпляр API. Для кількох
  доведеться переходити на PostgreSQL — але для трекера звичок
  на десяток користувачів це передчасно.
- Межа довжини назви (100 символів) продубльована в `bot/api.py`
  константою `MAX_NAME_LENGTH`. Бот підрізає значення сам, щоб людина
  бачила зрозуміле пояснення, а не `422` від сервера.
